## Decision and ownership boundary

An explicit procedure can complete a newly instrumented, proven-owned synthetic
orphan. The intended fields already come from the reviewed original journal
preimage and canonical size intent; no additional product specification is needed.

The old retained orphan has no durable binding from native insertion ID to its
migration operation. A matching parent, time or absence from an earlier inventory
cannot supply that missing historical evidence. It stays refused. This rehearsal
does not manufacture an ownership receipt for it, adopt it, delete it or close
gate 4 overall.

For a real historical orphan, the missing input is authenticated creation/audit
evidence tying the exact native child ID to the operation. Owner approval does
not substitute for that evidence or waive the adoption proof. Any future
owner-authorized resolution contract would be a separately scoped decision,
not implemented here and not evidence of insertion ownership. These synthetic
cases provide no historical ownership or live repair authority.

## Explicit procedure exercised locally

1. Start a new synthetic conversion with an empty pre-insert child inventory.
   In the native three-argument insertion hook, require `update === false`, the
   active create-child intent and size, matching parent/preimage/plan/revision/
   writer token, and ownership of the live database lock. Persist and read back
   the exact child ID/raw rows, connection/process and case binding before the
   injected interruption; require a separate durable receipt acknowledgment.
2. Inspect fresh state without mutation. Bind a repair approval envelope to the
   exact receipt hash and full current preimage. The preimage covers normalized
   product state, raw parent/child posts and metadata, relationships, referenced
   terms/taxonomies, lookup rows and both journals.
3. Explicit repair acquires the parent lock, disables reconnect/replay, checks
   autocommit and all relevant InnoDB tables, rereads the approved state and
   validates the prospective ownership proof. A separate CAS repair journal
   records its own token and mutation attempt. The migration remains FAILED.
4. Fill only the proven child using native CRUD and the original intended fields.
   Never delete or replace it. Settle only the approved parent's native deferred
   synchronization under the fence, then record exact settled afterimages.
   Native shutdown synchronization is removed for this private worker, so a
   failure cannot leave product writes queued after the fence is released.
5. Stop at REPAIRED_AWAITING_REVIEW. Inspect fresh native state again and provide
   a separate resume approval. The helper never generates that approval or calls
   core resume automatically from repair.
6. A separate command holds the parent lock across full approval validation and
   unchanged core resume. Native after-child synchronization occurs while the
   core is incomplete. Parent save and deprecated-sync boundary assertions must
   be the last registered callbacks and require the same lock, incomplete guard
   and empty queue. Only the core's final exact readback can reach COMPLETE.
   Nested lock releases are checked for balance; post-COMPLETE checks are read-only.

The driver supplies **simulated explicit operator-review envelopes** between
separate native processes. This tests command boundaries, not independent human
approval of each individual receipt. Independent review covers the code and
saved execution evidence.

## Qualification and limits

Use `evidence/results.json` and `manifest.json` for the completed run, exact source
pins and final disposition. Earlier failed/superseded runs are preserved separately.
Raw command receipts remain local and are indexed by hash; this is not a raw-data
or inventory upload package.

The positive path retains the original proven child ID, completes six literal
Kids-size strings through separate repair/review/resume, and preserves persisted
order identities and amounts. Failure controls cover missing or unacknowledged
receipts, forged update flags/IDs/parents, stale and raw-only drift, unexplained
children, concurrent repair/connection loss, interrupted repair, lock-time review
races and late native synchronization at both boundaries. Foreign-parent rows
must remain unchanged.

Unrecorded partial repair, unexplained drift or missing insertion provenance
remain manual investigation. A fresh digest is not evidence of ownership and
cannot legitimize unexpected data. Four-mode commerce qualification belongs to
the unchanged delivered subset; this extension uses the stated native fixture
mode and is not another all-mode or 31-product migration batch.

Gate 4 still needs an accepted resolution for unproven historical/partial states,
installed-stack qualification, reviewed native IDs and preimages, in-flight
commerce quiescence, and explicit live conversion/recovery authority. Complete
backup, isolated restore, newer-order-preserving rollback and publication gates
also remain open. No production conversion, real order/payment, live order synchronization,
deployment, publishing or provider action was performed by this extension.
