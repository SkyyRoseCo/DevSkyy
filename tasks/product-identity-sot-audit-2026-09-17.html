4. Proposed schema — additive, nothing renamed, nothing moved

This is not a greenfield schema. It is logo-registry.json edited in place: new sibling sections added, product_registry_schema_version bumped 1 → 2. Every existing key name is preserved byte-for-byte, because products[sku].catalog.* key names are load-bearing across 116 consumer files, the catalog_columns ordering, and PHP array reads such as ['garment']['sizing_references']. Renaming would turn a mechanical migration into 116 edits.

Organization — enforced, not aspirational

A SOT that 116 files read has to stay predictable, so the organization is now machine-checked rather than described. Three properties, all live today [test]:

PropertyEnforced byCurrent state
Schema-valid — required fields, SKU pattern ^(br|lh|sg|kids)-[0-9]{3}$, collection slug from a 4-value enum, booleans as "0"/"1" strings, image paths under assets/, and additionalProperties: false so a typo'd key is an error rather than a silent new fielddata/logo-registry.schema.json (JSON Schema 2020-12)0 violations across all 33 SKUs
Internally consistent — catalog.sku matches its key, catalog_columns is satisfied by every record, and every declared image exists on diskscripts/organize_product_registry.py --check0 violations; no record points at a missing image
Canonically ordered — fixed top-level section order, fixed per-product section order, catalog keys in catalog_columns order, SKUs sorted by collection (SIG → BR → LH → Kids) then numbersame script, --apply35 order findings — cosmetic, see below

The reading order tells the story: what the file is → who governs it → the brand → the products → the graphics → the projection contracts → history. Per product: commerce → the physical garment → the founder's specification → what represents it → what it's rendered from → copy → corrections → who vouches for it.

Ordering is the only open finding, and it is purely cosmetic. Proved losslessly: the reordered registry compares deep-equal to the current one (tests/test_registry_organization.py::test_reordering_is_lossless) — Python dict equality ignores key order, so an equal compare after reordering proves no value moved, dropped, or was coerced. Its benefit is diffs: today a founder edit can surface as a reshuffle in a 436 KB JSON; after the rewrite it is one changed line, which is what makes review and git blame usable on this file.

It is left unapplied on purpose — a whole-file rewrite would collide with the uncommitted codex/unified-product-registry work. Run it once that lands: python scripts/organize_product_registry.py --apply. The script refuses to reorder while any schema or consistency finding is open, so it can never paper over a real defect.

5. Two rules that must ship with the schema

Per-section authority, not one blanket string

Today authority is the single string "FOUNDER_PRODUCT_SPECIFICATIONS" on all 33 SKUs. After the merge, the same record would hold founder-verbatim corrections, agent-written marketing copy, and — if absorbed — machine vision output, all under that one string. That collapse is the defect the merge would introduce. The file already sets the precedent: garment.fit.source: "founder product dossier". Extend it per section so FOUNDER_CONFIRMED stays distinguishable from everything else.

Vision analysis stays out of the product record

garment-analysis.json is Gemini 2.5 Flash vision output on 58 SKU references. Folding it in as product fact re-creates the contamination vector behind bug-096 — 30 SKUs of hallucinated brand canon across 120 renders — and the dossier-contamination findings from the render review. Dossiers are founder-authored, never ML-drafted. It is referenced from a fenced derived/ section that no render prompt reads, or left where it is.

6. Constraints already decided by the evidence

The SOT is private; the storefront gets a generated projection

Three verified facts force this:

  1. inc/product-catalog.php:50 reads data/logo-registry.json [repo]
  2. scripts/deploy-theme.sh excludes data/logo-registry.json from the deploy rsync [repo]
  3. The file carries 200,881 chars of design specification — shipping it publicly publishes every product's build sheet

So the PHP catalog is currently reading a file that never reaches production. This is a live deploy blocker independent of this migration, and the fix is the same either way: the theme consumes a generated public runtime projection (commerce + image bindings only, no dossier bodies, no render sources), and the authored file stays out of the deploy. Your "one file for everything" choice is about authoring; this is the implementation it implies, not a contradiction of it.

Name collision with the four collection files — resolved by the correction

Four files are already named identity.json at data/collections/<slug>/identity.json. They are the canon seed for a generator chain — build-collection-sot.py → sot.json, gen-design-tokens.py → design-tokens.css, gen-collection-hub.py → index.html, all loaded through sot_common.load_identity(). Code consumers found: those four generators plus verify-collection-sot.py, tests/test_collection_sot_guard.py, tests/collections/test_sot_common.py, tests/collections/test_gen_collection_hub.py, and .claude/hooks/catalog-drift-guard.sh. Absorbing them means repointing sot_common.load_identity() — one function — and docs/CLAUDE.md:11, which still documents them as the per-collection SOT.

Keeping the product facts in logo-registry.json removes the whole collision problem. Nothing renames, so no reader of the product spine changes; the only path edit in the entire migration is that one load_identity() function, and the four collection files get deleted once their content is folded in — after which identity.json means exactly one thing.
