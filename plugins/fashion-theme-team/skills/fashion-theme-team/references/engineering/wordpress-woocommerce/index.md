# WordPress / WooCommerce engineering references

On-demand references embedded from two founder-authored DevSkyy skills. Load a file only when its "Load when" line matches the task; `skyyrose-wp-platform/overview.md` is the router for the four files beside it.

## Placeholders

- `<theme-root>` — the SkyyRose theme directory. In DevSkyy: `wordpress-theme/skyyrose-flagship`.
- `<theme-workspace>` — the parent of `<theme-root>`, where `package.json` and the Node `.min` build live. In DevSkyy: `wordpress-theme/`.
- `<repo-root>` — the host checkout root.

## Authority rules applied to every file

- **Product source of truth.** The single editable product source of truth is `logo-registry.json` (in DevSkyy a root symlink to `<theme-root>/data/logo-registry.json`). Its `products[sku]` records own commerce fields, colors, sizes, fit, materials, design spec, and image bindings. The catalog CSV and per-SKU dossiers are generated projections, read through sanctioned readers (`skyyrose.core.product_registry`, `catalog_loader`, `dossier_loader`, `sot_images`, `LogoRegistry`), and never authored. Every source line that named the catalog CSV, dossiers, `inc/product-catalog.php`, or `sot-images.json` as the source of truth was rewritten to this rule.
- **Founder authority.** Corey, the founder and maker, is authoritative on his own product specs: his confirmations are recorded as `FOUNDER_CONFIRMED`, and no third-party verification is demanded of his facts.
- **Plugin boundary.** Outside plugin scope — the Fashion Theme Team builds and reviews candidates only; production deploys, live WooCommerce/media writes, and paid calls belong to the host repo's STOP-AND-SHOW approval process. Verification knowledge (what to check after a deploy) is kept for review.
- **Host-only tooling** (`.wolf/`, `scripts/deploy-theme.sh`, `scripts/wolf_bug_id.py`, `.env.wordpress`, DevSkyy Python modules, DevSkyy skill and agent names) is kept as an explicit "Host repo (DevSkyy):" note rather than deleted.
