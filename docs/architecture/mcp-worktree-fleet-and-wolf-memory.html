MCP Servers: Worktree Fleet + Wolf Memory

DevSkyy · 2026-09-16 · BUILT — 46/46 tests green, registered in .mcp.json · scope: single machine (theceo), Claude Code + Codex as co-tenants of this repo
Deviations from the original spec, decided during implementation:
  • Skipped reusing mcp_tools.security.secure_tool and mcp_tools.api_client._format_response — both transitively import mcp_tools.server , which constructs the devskyy FastMCP app as an import side effect. That breaks the "zero backend coupling" property these servers exist for, and rate-limiting/dedup target a different threat model (public API abuse) than what these internal, trusted-agent tools need. mcp_servers/_shared.py reimplements the response formatter locally instead; only mcp_tools.types.BaseAgentInput -equivalent shapes were kept, hand-written (pure pydantic, zero side effects either way).
  • Both founder-decision open questions were resolved with the spec's own recommendation, per instruction to proceed: branch/no-DB-row conflicts adopt silently; bug_bump only surfaces the _recurring_sync_needed flag rather than auto-triggering wolf_recurring_sync.py itself.
  • A real SQLite WAL-mode first-touch race under concurrent process startup was caught by the cross-process test suite (not anticipated in the spec) — fixed by checking the current journal mode before attempting to change it, with a small bounded retry for the rare first-time transition.

Two standalone MCP servers, ranked #1 and #2 out of a longer list because usage data (not recall) showed they're the only candidates that clear all three bars: a consumer other than this Claude Code session needs them, they need atomicity that file access alone can't give, and a founder-mandated policy needs to become an enforced gate instead of prose.

Shared foundations

Both servers are standalone FastMCP processes , not new tool modules bolted onto mcp_tools/ (the existing devskyy monolith). Reasons this repo already gave us:

  • Second consumer is real, not hypothetical. This session is running on branch codex/v2-open-seo-security-audit — Codex already works in this repo alongside Claude Code. Codex has its own MCP client config; a server coupled to devskyy_mcp.py 's FastAPI backend URL / API key plumbing isn't something Codex can trivially point at. A small standalone server with no backend dependency is.
  • Zero backend coupling. Most mcp_tools/ modules call _make_api_request against DEVSKYY_API_URL . These two servers touch only local files ( git , .wolf/* ) — they should work with the FastAPI backend down.
  • Convention match. Reuse what already works: BaseAgentInput (pydantic, extra="forbid" , response_format field) from mcp_tools/types.py , the secure_tool decorator from mcp_tools/security.py , and the confirm-gated-mutation pattern already proven in wc_update_product . Each server still creates its own FastMCP(...) instance — importing types/security helpers is fine (pydantic-only deps), importing mcp_tools.server is not (pulls in the backend config).
  • bug-263 applies verbatim. Both entrypoints shell out via subprocess ( git worktree … ) and both are long-running stdio processes on darwin — the exact conditions that caused the SIGSEGV pattern logged 8× in .wolf/buglog.json . Both entrypoints open with the same guard devskyy_mcp.py uses: 
    if sys.platform == "darwin":
    os.environ.setdefault("no_proxy", "*")
    os.environ.setdefault("NO_PROXY", "*")
    before any other import.
  • The concurrency model, stated once because it drives every design choice below: stdio-transport MCP servers are one subprocess per connecting client . Two Claude Code sessions (or Claude Code + Codex) each spawn their own process — there is no shared memory between them. So "atomic" cannot mean an in-process lock; it has to mean a lock that lives in the shared file both processes touch. Both servers use a small SQLite file opened in WAL mode, with every mutation wrapped in BEGIN IMMEDIATE to take the write lock up front (SQLite's default deferred locking still races under concurrent writers — BEGIN IMMEDIATE closes that gap). SQLite is used as a lock + counter , never as a second data store — the human-readable, git-tracked files ( .wolf/buglog.json , .wolf/cerebrum.md ) stay the sole data SOT, matching the "never fork a SOT" principle this repo already applies to product data.
Explicit non-goal: this design is single-machine. Memory already records a two-machine setup (theceo + coreyfoster). A SQLite file is not safe to share over a synced folder (iCloud/Dropbox) — two machines writing the same SQLite file over a syncing filesystem is a corruption risk, not a coordination mechanism. Cross-machine dedup is out of scope here; it would need a tiny shared HTTP endpoint, which is a bigger, separate proposal.

1. Worktree Fleet server

Evidence, not opinion: git worktree was invoked 233×/30 days — the single heaviest non-file-read Bash command in this session's history ( rtk discover ). 32× rmdir against .codex/worktrees/* shows a second tool cleaning up the same kind of state. Memory holds three separate stranded-worktree incidents (2026-06-09, 2026-06-18, 2026-09-10 — the last one needed 44 worktrees manually reaped, some requiring "wip: snapshot" commits to avoid losing dirty work). git worktree list alone doesn't tell you who owns a worktree, why it exists, or whether its work already made it to a branch — that's exactly the information every past sweep had to reconstruct by hand.

Data model

SQLite file: .wolf/fleet.db (add to .gitignore — machine-local, ephemeral coordination state, not portable across the dual-machine setup). 

CREATE TABLE worktrees (
  path         TEXT PRIMARY KEY,
  branch       TEXT NOT NULL,
  repo_root    TEXT NOT NULL,
  owner        TEXT NOT NULL,   -- caller-supplied agent/session id, e.g. "claude:37b5c934"
  purpose      TEXT,
  status       TEXT NOT NULL DEFAULT 'active'
               CHECK (status IN ('active','ready_to_merge','merged','abandoned')),
  pushed       INTEGER NOT NULL DEFAULT 0,
  created_at   TEXT NOT NULL,
  last_seen_at TEXT NOT NULL,
  closed_at    TEXT
);

Identity note: MCP over stdio gives the server no reliable notion of "which agent is calling" beyond what the client declares. owner is a required parameter, not something the server infers — every tool call must pass a session/agent id the caller controls (Claude Code sessions already have one; a Codex call would pass its own).

Tool surface

Tool Params Behavior
worktree_claim branch, purpose, owner, base_ref="main" Fails if branch already has a live registry row owned by someone else. Otherwise runs git worktree add , inserts the row inside BEGIN IMMEDIATE . This is the actual race fix: two sessions requesting the same branch name at the same instant — only one wins the insert.
worktree_heartbeat path Bumps last_seen_at . Lets worktree_list distinguish "actively worked" from "opened three weeks ago and forgotten."
worktree_list status?, owner? Registry rows joined against live git worktree list --porcelain . Flags drift both directions: DB rows with no matching git worktree (already removed outside the tool), and git worktrees with no DB row (created manually, unregistered). This is the manifest every past sweep built by hand.
worktree_release path, verify_pushed=true, force=false Fail-closed by default. Refuses unless git log @{u}.. is empty and git status --porcelain is clean, and says exactly what's unpushed/dirty when it refuses. force=true bypasses the check — the tool's own description states this is a data-loss-risk override the calling agent must already have explicit human confirmation for, mirroring the confirm: bool gate already used on wc_update_product . The tool cannot itself pause for a human mid-call; the STOP-AND-SHOW happens one level up, before the agent ever sets force=true .
worktree_prune dry_run=true, ttl_hours=24 Actually removes only rows already ready_to_merge / merged past the TTL. Anything that looks abandoned (no heartbeat, dirty or unpushed) is only reported , never auto-deleted — this is the direct fix for "stranded commits ≠ stranded work."

2. Wolf Memory / Bug-Log server

Evidence: .wolf/buglog.json shows real recurring cost — bug-096 ×30, bug-172 ×24, bug-263 ×8, bug-230 ×7, bug-231 ×5 — and OPENWOLF.md states outright: "past cross-session collisions came from manual ID guessing," which is exactly the TOCTOU race you get from "scan the JSON for the max id, add one" under concurrent writers. Separately: buglog.json is 337KB and memory.md is 534KB — every current workflow that "reads buglog.json first" or appends to it is a full-file round trip at that size, which is itself a token cost this server removes by exposing scoped operations instead.

Data model

.wolf/buglog.json stays the sole data SOT — same schema OPENWOLF.md already mandates ( id , timestamp , error_message , file , root_cause , fix , tags , related_bugs , occurrences , last_seen ), still git-tracked, still human-diffable in PRs. cerebrum.md and memory.md stay Markdown, edited by structured append, not rewrite.

New: .wolf/wolf.lock.db (gitignored) — a single-row SQLite counter table, used purely as an atomic sequence + write-mutex for the JSON file. It holds no bug data. 

CREATE TABLE counters (name TEXT PRIMARY KEY, value INTEGER NOT NULL);
-- one row: ('bug', <last allocated N>)

Tool surface

Tool Params Behavior
bug_next_id — BEGIN IMMEDIATE → UPDATE counters SET value = value + 1 WHERE name='bug' RETURNING value → format bug-NNN . Replaces scripts/wolf_bug_id.py 's scan-and-guess with a real atomic increment. Existing script can become a thin CLI wrapper around this tool instead of being deleted outright.
bug_log error_message, file, root_cause, fix, tags[], related_bugs[]=[] First checks for a near-duplicate (same file + substring match on error_message ); if found, calls the same path as bug_bump instead of creating a new id — this is the "bump occurrences, never duplicate" rule from OPENWOLF.md, enforced instead of hoped for. Otherwise allocates via bug_next_id and appends atomically: read-modify-write of buglog.json happens inside the same SQLite transaction that holds the lock, so two concurrent bug_log calls can't interleave and corrupt the JSON array.
bug_search query, tags?=[], min_occurrences? Grep-equivalent scoped search over buglog.json — the "read buglog before fixing" step every session is supposed to do manually, as one call instead of a full-file read.
bug_bump id Increments occurrences , updates last_seen . When the result crosses occurrences >= 2 , the tool's return value explicitly flags that scripts/wolf_recurring_sync.py needs a run — today that's a rule the agent has to remember; this makes it a returned fact instead.
cerebrum_append section (enum: preferences / learnings / do_not_repeat / decision_log), entry Structured append under the matching ## heading in cerebrum.md . The enum makes misfiling (wrong section) structurally impossible instead of relying on the agent picking the right heading by hand.

Build order

  1. Wolf Memory first — smaller surface (no git subprocess calls, no destructive-op design), and it directly de-races a bug that's already bitten this project by name.
  2. Worktree Fleet second — same store/lock pattern, reused; the new work is the git-command layer and the fail-closed worktree_release checks.
  3. Register both in .mcp.json once tests are green; note the Codex-side config separately since its MCP registration format differs from Claude Code's.
